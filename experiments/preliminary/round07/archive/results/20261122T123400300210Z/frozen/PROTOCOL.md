# 第 07 轮：对照修订与两个新基础任务的小规模配对

先复核 06，见 REVIEW06.md；原 06 全部保留。修订版本以申报书 3.1.4 同状态续行比较为方法，不训练、不生成偏好标签，不宣布总体收益。该轮目的为在商品和支付方式变化时复查现象是否重复。

## 样本及来源

公开本地 τ²-bench 零售 tasks.json 任务70（头盔，信用卡）及52（相机，PayPal）。完整原任务、给定历史、变更消息、私有用户规则和数据哈希分别存入 scenarios。使用官方期望换货 action 作为已获确认旧方案，公开工具记录按原数据库构造；不声称该历史由模型从头办出。相机任务沿用其官方 action 的30MP旧替代品；原自然语言要求与官方 action 的具体规格未必完全相合，本轮只研究显式给定旧计划后新消息的受控续行，不计算原生官方完整任务成功率。

70：已确认M/蓝/高通风方案，用户改为黑/高通风必要、M优先，不能假定接受L；模拟用户允许有货的L/黑/高通风。52：已确认30MP/10x/SD方案，改为30MP/CF必要、10x优先，不能假定接受较低变焦；模拟用户仅允许有货的5x/30MP/CF，不允许3x。数据库和价格不修改。两任务均单商品，未扩展为多单业务。

每任务两个认识状态：已有可用替代品库存证据、同一变体库存观察被遮蔽为null。仅改历史中的一个 available 观察，目录其他规格/价格、真实数据库、目标、规则不变。所有派生状态从这条观察生成。每状态比较库存依据先行与许可澄清先行，各重复两次：每任务8条续行，共16条。配对内完整起点相同；相邻状态比较的库存工作分别为缓存整理与真实查询，不是同一低层动作。

## 职责及工作契约

状态 `s=(g,F,C,H,P,D)`，输入 `x=(s,d,A)`，完整首指令 `ν=(a,z,K,e)`，后续共同策略 π_c。程序负责依赖、库存四值、候选合法性、逐项金额、权限触发、参数验证与写入门禁；LLM负责变更和许可语义、工作比较、提问及新方案确认措辞。模型依然能看到原目录，筛选工作的增益仅是显式程序候选归纳，不新增信息；这一重叠是设计局限。

首步在业务上可执行且有预期输出：known的screen产生确切候选整理，clarify可以直接基于可见目录问许可；unknown的inventory补库存，clarify可先获得条件规则。screen不是强制环节：一旦有许可规则、有效许可或当前方案，就不再提供无必要的screen；有规则时不重复问同一许可。unknown时无库存不得准备方案。inventory包含官方查询及派生候选；故未知两分支可能最终都做同样必要工作，只是顺序不同，不能要求它们必须形成成本差。

所有具体变体许可统一写成库存为真的条件规则；LLM即使认为是直接许可，程序也先看证据，unknown/false不能激活。规则保存原句、用户来源及库存来源；许可范围仅此具体变体，不代表最终交易批准。获得当前完整方案明确授权才可提交。程序不以关键词判定自由语义，许可和批准仍由LLM抽取并核验引用。

06 的底层 Ledger 保留，仍在prepare和confirm进行匹配/金额复算。这是共同执行器的重复安全复核，报告会列出，不能当成新增信息。新增菜单屏蔽仅去掉已无缺口的额外整理，不保证全局最小计算量。

## 校验、冻结、上线

使用现有 tau2-official/.venv/Scripts/python.exe。依次 `run.py check`、`run.py freeze`，再进入该批次 frozen 执行 `run.py execute`。离线不调用模型；8个机械路径（2任务×2状态×2首步）、条件许可真值表、卡尾号反例、起点/唯一观察差、授权门禁和菜单重叠全部通过后才冻结。规则、预算、代码、场景和评分预先哈希。运行中不修复、不重试、不替补；失败及接口错误保留。线上后续分析只读，另存审计，不改分。

统一请求 deepseek-flash，temperature=0、thinking=false、retries=0、timeout=60。每条Agent预算24次、60000 total tokens、9工作。输出上限：共同控制器1400、worker1000、回复解析1000、必要参数选择1000；公共语义700；模拟用户700；外部评审1400。继承事后扣词元机制，末次可超剩余，之后停止。每任务每重复新采一个公共语义解析，供四条后缀共享；与预注册语义不一致则该重复初始化失败，不替换样本。公共语义不是研究目标。

按任务70→52执行；每任务重复1为known(screen,clarify)、unknown(clarify,inventory)，重复2倒序。每条均新调用，温度0仍可能波动，记录返回模型别名/指纹/ID，不假设服务提供更细权重版本或可固定随机种子。

## 分离评分与投入

预注册多维结果见 scoring.json。R_write只看真实DB按传参写入；R_goal看是否符合最新用户可接受目标；C_hard核对规格、真实库存、完整范围、支付、精确金额；C_authorization_program核对新方案绑定；C_permission_state核对有效许可不得先于库存；T_payment_description用确定性“ending...”检查；外部评审分别判断同意和其他表述，返回具体原句与ref。T_claims综合确定性支付检查与外部评审，缺失评审为未知。各原分量保留，strict_pass为明确且通过的交集，不冒充全面语义证明。

表述检查不只看工具接受；支付ID与last_four分开向worker供给。确定性检查只覆盖明确尾号句式，不宣称覆盖全部自然语言；外部评审依然可能漏检，最终另读原句。模型评审不决定R_write，不覆写机械结果。

先逐任务逐条报告结果，再看进展、保留、阻塞、重复功能、调用及词元。续行Agent、公共前缀、模拟用户、外部评审四账分开；不扣供应商缓存输入。只在质量各维均通过且审计无冲突时比较配对资源；n=2仅描述方向和变动范围，不显著性推断或偏好标签。观察到的轨迹现象与可能机制原因分别写，修订版不能与06不同实现的数值直接作收益比较。
