# 第26轮方案｜申报前在线 API 实验收尾

2026-11-26 · 方案草案，正式样本、评分规则和预算在联调后冻结。第25轮按需调度验收是本轮的前置工作。

## 1. 本轮要回答的问题

沿用申报书 2.1 的两问。本轮分别形成两类前期证据。

1. **框架效用。** 状态约束与建模、认知决策、任务执行与反馈能否在两类实际业务中形成闭环？在同一模型与同一动态业务环境下，框架相对于官方 Agent 的收益体现在哪些情形？
2. **样本可用性。** 能否从可复现的同状态续行和自主决策中，制成内容可核验、格式可读取的监督微调示范和偏好样本？本轮验收到数据导出、字段检查和来源复核。

把已核对的官方失败机制作为个案纳入分析。案例和对照条件在正式运行前确定。运行结束后按所有预先选定的题报告结果。

## 2. 前置验收与正式入口

### 2.1 第25轮确认按需调度

用第25轮已配置的4道题，比较逐步版和按需版，各2组×2次，共16条。状态、决策规则、执行器和模拟层保持一致，单独比较调度。核对需要语义理解或选择时是否仍交给模型，前提明确时是否减少例行调用，最终操作是否绑定有效授权。

此批用于选定后续框架版本。若出现旧方案未经确认被提交、约束冲突被程序当作条件齐备，须先修复对应路径，另记版本并复验。将最终版本锁定后再开展外部对照。

### 2.2 退货业务适配与共同环境

第25轮的执行器支持换货。正式批次增加**退货**，采用官方的 `return_delivered_order_items`、退货退款规则和数据库终态 `return requested`。框架仍由三个模块共同工作，业务适配记录应说明哪些逻辑沿用、哪些规则和工具因业务而变。

退货离线验收至少覆盖订单状态、应退商品或退款方式更新、原确认失效、重新确认、完整的原生工具写入、用户撤回后的不写入。若两类业务仍未具备相同的事实判定口径，继续完成轨迹筛样等独立工作，端到端批次等接口验收通过后启动。

共同模拟环境须能回答关于金额计算依据或退款方式的合法追问。对澄清提取，应区分当前报价和已明确否定的选项，用户自然语言回复须与内部许可一致。金额在构造任务时统一量化至分。事件在同一公开业务节点触发，工具更新以相同工具记录交给两组。先用另选的联调题核对这些条件，联调题和正式题分开保存。

## 3. 主实验 A：两类业务的端到端配对

### 3.1 任务规模

- 目标 **20道独立基础任务**，建议换货8道、退货12道。每类同时包含稳定与变化题，动态类约占三分之二。所有正式题事先完成订单级去重，并排除参与调试的订单。
- 任务按选题表固定为稳定参照、证据待获取、条件变化、相互依赖的规则或授权冲突。每项变化有可公开观察的来源与时点。若采用原题子任务或从公开数据库构造新情景，留存原始出处与改编说明，并标注为受控任务。
- 每题两组各跑一次，共 **40条主轨迹**。另在冻结前指定4道代表题，各组再重复一次，共 **8条复验轨迹**。复验与原题同属一个基础任务，分开报告波动。
- 题源初筛基于本地官方任务文件。换货参考动作覆盖24个不同订单，退货覆盖27个。与仓库已登记的 case.json 对照后，暂有7个换货订单、17个退货订单未命中该清单，其中换货候选尚含当前行级状态表示不支持的第105题。此处是初筛，冻结前须结合历轮清单和实际日志再次排重。换货8道的缺口可从公开库中另选未使用的已交付订单构造受控任务，采用预定的选择规则和同一政策。

### 3.2 适合检验优势的任务

| 场景 | 换货 | 退货 | 关键观察 |
|---|---|---|---|
| 稳定参照 | 目标规格、库存、付款信息已明确 | 商品范围、退款方式及订单满足条件 | 正常办结和例行调用 |
| 证据不足 | 规格和资源还有一项需要查证 | 商品范围或合规退款方式尚未确认 | 是否先解决真实缺口 |
| 办理过程变化 | 旧方案确认后库存或一项规格变化 | 用户改变应退商品或退款方式 | 是否复用有效依据并重新确认当前方案 |
| 约束冲突 | 所需规格有货但总差额违背金额要求 | 用户提出不可用退款方式，或原范围已改变且批准只覆盖旧方案 | 能否转向合理澄清、避免直接执行旧方案 |

其中后两类能说明框架的约束判断和状态更新有何作用。若出现官方失败，逐条核对错误是否先于模拟偏差、实际有没有提交、框架如何从同一公开起点处理。横向表保留双方均正确、单方正确及双方失败的原始结果。

### 3.3 对照与指标

两组共用基础模型与参数、原生政策、工具数据、公开初始信息、事件时点、用户规则和独立评分。官方 Agent 保留原生循环与工具能力。框架侧使用通过验收的按需调度版本。两组都允许提出不同但合理的查询和澄清方式。按题和重复交替两组运行顺序，空间允许时分开记录缓存首次使用及重复使用。

- **主指标**为合规正确办结。用实际工具调用与数据库终态核对订单、商品范围、支付或退款方式、金额及当前授权。合理地拒绝或暂停的题仅在预先给定相应正确结局时计为正确。
- **过程证据**记录变化后的首个关键工作、处理对象、引用依据及下一轮状态，区分模型原始选择、程序拦截与实际写入。首次出现的过程错误即使后来修复，也单列。
- **投入**记录 Agent 的认知、语义及执行调用，模型词元、缓存和耗时。模拟用户独立记账。在同质量且无已确认模拟偏差的配对中比较投入，同时公开全部正式轨迹与排除原因。
- 最终按业务类型和场景报告基础题分母、配对差异以及失败原因。至少保留两条代表性轨迹：一条能解释差异，另一条展示两组都能合理推进，或展示框架遇到的局限。

## 4. 同批实验 B：轨迹和微调数据的可行性

### B1. 自主示范

以第24轮的12条可审阅例为起点，并从新版主实验采集**自主查询和自主分析**的候选。使用原始模型请求还原当时可见的输入。记录模型实际选择、执行结果、后续是否推进、来源和基础题编号。程序自动推进和实验强制首步单列使用。导出 SFT 文件，逐条复核示例覆盖、字段与原始轨迹。

### B2. 同状态偏好

预先确定 **3个检查点**，覆盖两类实际业务，其中至少有一个是未参与调试的新任务。每个检查点选两个确实可执行的首步，从同一状态分别执行，使用相同续行策略、用户规则和评分方式，各重复两次，共 **12条续行轨迹**。

评价顺序为硬约束、正确办结、用户已明确表达的业务偏好、处理投入。记录工作类别及具体对象或报价。若要比较“先分析还是先澄清”本身，可补离线核对同一报价，防止把报价对象带来的差异全算在工作类别上。结果相当、排序反转或被执行及模拟异常干扰的配对单独留档。

对稳定且有明确理由的配对，将同一可见状态与两个合规格式的决策序列导出为偏好样本。保留源轨迹与评分理由，验证两个候选共享输入，且历史、未来反馈和程序内部信息边界正确。按基础题登记可用于后续训练、验证及待保留的新题，防止同题分支跨集合。

### B3. 交付和退出点

交付 SFT 样本、具备明确方向时的偏好样本或候选表、未通过的条目及原因，并用本地进程验收训练字段、输入边界和来源引用。该步骤完成即可在申报书里报告“形成可读取、可追溯的微调样本”。训练和小模型效果验证属于后续同接口实验。

## 5. 收尾、数量与报告

- 已计划正式运行上限为 **76条轨迹**：第25轮机制复验16条，主实验40条，预先选定重复8条，同状态续行12条。小批联调另记，优先用离线回归解决环境问题。联调后冻结每条和每阶段的调用预算、停机条件及模型配置。
- A 和 B 各自留档。A 的适配或模拟调试期间，B1 离线筛选和数据验收可先完成。B2 宜在新版执行契约验收后运行。
- 正式前固定任务顺序、样本数、判定规则、失败及异常处理。正式后不因组间表现或优势方向加题、换题或重跑。环境或实现问题需要修复时，保存原始正式批次，重新冻结并只复验事先明确受影响的部分。
- **申报书用的产出**为一张跨换货、退货的官方配对结果表，两条能追溯三个模块的代表性轨迹，及一组经过校验的 SFT 与偏好示例。结论写清优势出现的条件、实际样本规模和失败原因。若两组办结表现接近，仍可报告预先记录的状态使用与处理投入差异。
