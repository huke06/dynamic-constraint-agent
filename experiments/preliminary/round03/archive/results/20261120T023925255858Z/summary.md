# 单任务续办结果

使用 τ²-bench retail 任务 0 的官方数据库、政策和工具，在共同确认前缀之后，由用户消息只修改键盘规格。两组各一条续办轨迹，执行模型均为 `deepseek-flash`，相同执行提示和官方工具 schema；完整框架额外维护带版本、来源和依赖的判断状态。

|观察项|直接判断组|完整框架组|
|---|---|---|
|执行回合|3|3|
|自主工具/沟通顺序|calculate → 告知并请求确认 → exchange_delivered_order_items|相同|
|身份、订单、商品重复查询|0|0|
|按新规格、金额重新确认|是|是，并明确说明旧确认不覆盖新键盘|
|两件商品一次性正确提交|是|是|
|最终合计退款|59.68|59.68|
|根据轨迹复核的合规办结|通过|通过|
|显式状态依赖缺陷|无该模块，无法评价内部依赖|出现 1 个不存在的依赖编号；保留为未知|

两组最终均提交 `1151293680→3616838507`（tactile / white / full size）与 `4983901480→7747408585`（黑色 Google Assistant 恒温器），支付/退款方式为 `credit_card_9513926`。官方工具计算差价 -59.68，订单状态为 `exchange requested`。

两组的更新方案说明均在历史消息 18，用户明确同意在消息 19，写调用在消息 20（索引从 0 开始）。旧确认位于消息 14，变更用户消息位于 15。不存在把旧确认直接当成新方案授权的提交。原始文字与引用见 `semantic_review.json`。

框架第一次更新后，身份、阶段、旧商品、恒温器目标和支付依据记录原样保留，恒温器匹配判断仍为 supported、版本 1；旧键盘匹配、原合计差价和原整单授权不再标为 supported。该过程不是由预设失效清单驱动。与此同时，状态模型产生了一个缺失依赖 `f.updated_refund_pending`；引擎没有把它猜成正确编号，依赖它的判断为 unknown。后续模型自行根据新计算结果和新确认刷新了判断。

状态来源质量没有全通过：三个衍生记录只引用了用户说“改成/保持”的消息，未完整链接历史中的具体变体/价格或支付资料。没有修正这些语义来源后再给执行器；它们原样留在轨迹中。正确办结不能证明状态构造无误。

离线 9 项检查通过；实际工具、状态补丁和原始请求回放通过；两组开始历史与变更消息、工具 schema 一致，模型请求未包含评测端私有目标。85 个前两轮文件、申报文件及原始任务/数据库/政策哈希未变，官方工具源文件哈希亦核对一致。

这是一个开发中的单任务机制样例。两个工程中断及无重复采样的续跑过程见本实验根目录 `工程记录.md`。本轮没有观察到办结结果差异；不据此宣称框架优于直接办理，也不把修复后续跑视作预先冻结的独立正式实验。未扩大任务数，未训练模型。
