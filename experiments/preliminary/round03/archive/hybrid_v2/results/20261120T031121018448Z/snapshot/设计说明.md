# 对齐申报书的 LLM＋程序职责

依据申报书 3.1、3.1.1、3.1.2 的分工：程序维护结构化记录、检查明确条件、完成确定筛选和计算；LLM 解释表达与字段的语义对应、处理确认范围和选择后续工作。逻辑环节不等于每项都要多调用一次模型。

## 程序职责

直接读取已发生的官方工具调用及返回，维护身份、订单、用户支付资料、商品缓存和来源索引，不调用 LLM 重新抄录工具事实。规则适配器为每件商品建立 requirement→match→delta→confirmation 关系，total 依赖各项 delta，整单 authorization 依赖清单、支付、合计和逐项确认。匹配还依赖商品/订单证据。节点、依赖和来源由程序生成，不允许 LLM 自由创建编号或图边。

用户规格变化通过语义补丁进入 requirement；程序传播待复核状态，保留其他节点的值、版本和来源。旧确认作为历史记录保留；当前授权绑定具体配对、合计金额、订单和支付方式的规范化指纹。未变化商品的确认可继续沿用，不能把旧整单金额授权用于新方案。

缓存内精确条件筛选、同产品/库存/资格/归属检查、Decimal 差价计算和提交去重均由程序完成。多个匹配候选不按任务答案自动择优；无匹配返回空集，由 LLM 决定查询、澄清或其他处置。程序不根据私有评测目标代填新变体、规定工作顺序或自动向用户确认。

## LLM 职责

一次共享语义调用从已有明确确认与新消息解释旧方案和本次规格增量。用户回复到达时，仅解释相邻方案说明、回复及相关业务上下文，判断是否明确同意以及同意哪些条款；程序再核对其具体参数和金额。语义提取本身可能错，保存原文及结构输出，不把指纹检查当成语义正确性的充分证明。

执行模型自主决定当前需获取信息、复核、分析、沟通还是提交，自己选择工具和参数。两组均有官方完整工具与三项程序能力：review_items（按指定对象复核缓存）、prepare_proposal（检查并计算自选参数，不提交）、read_evidence（调取未压缩来源）。LLM 可直接使用已有事实，不必走固定顺序。

本适配器覆盖已认证零售订单的规格换货，支持已观察字段上的精确选项增量；不宣称已经实现任意优惠偏好、模糊排名、跨订单撤销或其他业务动作。超出范围应反馈，不用关键词猜语义。

## 上下文与投入

框架每轮只携带：身份/阶段摘要、当前每件商品要求、匹配和确认状态、金额和授权状态、最近工具反馈/用户消息、最近少量自然交互。商品完整库存、用户完整资料、整个依赖图及全部历史均保留在程序侧；缺失内容可通过来源引用调取。使用精确序列化，不通过 LLM 摘要压缩事实，不无声截断规则或删除证据。完整业务政策和工具 schema 两组一致。

工具返回不触发状态维护模型调用，最终写入也直接由程序回填。只有自然语言语义问题进入语义适配调用。两组共享最初语义解释，后续语义判断按实际对话发生；费用分别列执行、语义和客户模拟，共享费用单列，不重复或隐藏。不能承诺框架一定更省；应报告各轮实际 token 和调用。

## 公共检查与验证边界

两组采用同一程序检查：授权范围完整、同款有库存、符合当前归一化要求、金额正确、用户确认绑定当前方案、同订单仅一次提交。工具接收到的参数仍由模型选择。拒绝和误拒绝保留日志，不能只记录最终成功；金标准仅用于离线负例与事后评价，不进入语义或执行请求。

共同前缀沿用上一轮受控历史，并非新采样出的自然完整对话。两组起点相同，直接组读取原历史，框架组从该历史构建可调取的程序状态；因此实际模型上下文有意不同。该验证同时改变状态维护和上下文组织，尚不是二者的独立消融。与上一版公共提交检查不同，不能把新旧成功率直接比较。

先离线检查，再在同一个任务上各一条续轨验证并逐条核对更新确认与提交时序。保持申报书、旧实验、原任务及官方政策/工具不变。任何接口或解析错误保留，不隐去失败后反复采样直到成功。
