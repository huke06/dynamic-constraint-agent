## 1. 研究问题与范围

本项目围绕一个总问题展开。在动态多约束业务办理中，Agent如何依据业务状态作出认知决策，并利用执行反馈评价和优化决策策略？ 具体包括以下两个相互衔接的问题。

**（1）Agent如何依据动态业务状态合理开展认知决策？**

动态多约束业务中的事实、规则、资源和用户要求相互关联，局部条件变化可能使部分判断失效，同时保留其他有效依据。Agent既需要识别变化对既有结论及操作前提的影响，也需要在信息获取、条件分析和业务操作等多项候选工作之间作出合理选择。如何将动态业务状态及约束关联转化为持续认知决策的有效依据，并协调决策生成、任务执行和反馈调整，是本项目第一条研究路线要解决的关键问题。

**（2）如何利用执行反馈评价并提升Agent的认知决策能力？**

同一业务状态下可能存在多种可行的认知决策，其后续效果受到用户交互、环境变化及执行过程的共同影响。如何在可比条件下评价候选决策对任务完成、约束满足与处理成本的影响，并将评价结果转化为有效的模型学习信号，是本项目第二条研究路线要解决的关键问题。

第一条路线包含三个模块，依次完成**状态约束与建模 → 认知决策 → 任务执行与反馈 → 更新状态**。第二条路线从这个闭环采集轨迹，评价、学习并回接决策模块。当前以受控零售换货为磨合环境。社团系统用于后续应用验证。

## 3. 实验设计与评价口径

| 实验 | 问题 | 固定条件与主要观察 |
|---|---|---|
| **状态更新核验** | 哪些判断需要复核，哪些可以保留？ | 给定相同起始状态和事件，比较局部更新与全量复核的各项判定。记录变化来源、受影响范围、依据保留和授权失效。 |
| **框架内机制对照** | 显式候选和前提是否帮助 Agent 选对下一项工作？ | 同模型、状态、业务规则、工具和执行检查。对照组直接选择，实验组额外获得由公开状态构造的候选与前提。分别记录模型原始选择、程序核验、实际工作和后续状态。 |
| **官方 Agent 端到端基线** | 整套框架在相同业务环境中表现怎样？ | 固定模型、任务、可见业务事实、事件和核验口径。若使用项目改编的用户或事件脚本，结果标注为“官方 Agent 在受控变体上的对照”。原题、原用户模拟器和原评分的结果另列。 |
| **同状态候选续行** | 两个可行首步对后续办理的影响有何不同？ | 从同一快照执行不同首步。采用共同续行策略、用户规则和执行校验。在同一基础题内报告各分支与重复运行。 |
| **小模型训练与回接** | 决策能否学到，并用于未见任务？ | 固定状态接口、工具、校验和执行行为，只换决策模型。分别看关键状态的工作选择和完整任务表现。 |

**判定顺序。** 先看工作类别、业务对象和理由是否符合当时状态，再看必要前提、程序是否拦截及实际是否写入，最后看后续办理和最终结果。正确办结后仍记录重复查询、无效分析或重复询问。调用、输入输出词元、缓存和耗时作为辅助指标，模型侧与模拟用户侧分开记账。

**记录单位。** 基础任务是独立分析单位，状态变体和重复运行用于配对。运行前记录任务来源、修改的条件、可接受的选择及判定规则。同一状态可以有多种合理动作。记录正面结果、两组相当、结果反转及失败。按层汇报原始数和配对差异，并区分模型选择、语义执行、程序契约、环境及网络问题。

### 预先假设与主要指标

- **状态更新假设。** 给定相同的已观测变化和完整的依赖记录，局部更新与全量复核应得到相同的业务约束判定。主要指标为判定一致性和关键失效遗漏，另记复核的判断数量。
- **状态与决策假设。** 动态条件下的决策前提说明，有助于 Agent 选择当前可推进的工作。主要指标为首个关键决策的适切性，即工作类型和处理对象符合当前有效依据与必要前提。若观察到两组相同，进一步报告相同发生在哪些状态。
- **模型学习假设。** 在决策接口与执行校验相同的条件下，经核验的示范和偏好可以帮助小模型在未见任务中作出更合适的选择。以关键决策适切性为主要指标，完整办理与约束满足作共同核验。

正式批次开始前写明本轮只检验哪一项假设，预先记录主指标、任务与运行数量、预算和异常处理方式。固定后的批次按原计划报告，开发期间的修复与新增运行另记版本。

## 4. 当前要做的实验 · 前两阶段联合验收

**本轮主问题。** 框架已经知道当前方案不可行时，能否把这条判断转化为适当的后续工作，并在获得新事实或新许可后继续办理？

1. **先整理并修复第93题的三个断点。** 状态中区分原购规格、用户当前要求和最新获准规格。分析执行器允许“当前没有满足全部要求的方案”，并明确分析覆盖了哪些条件。决策模块收到这一结果后，可以分析备选、澄清可调整的要求，或在确实无法继续时说明原因。程序按最新状态校验拟案和提交。
2. **先用可重放轨迹离线核验。** 第93题分别检查“先分析”和“先澄清”是否都能按定义完成首步、产生有效反馈。加入正常路径与动态路径的参照，用第91题的有效工具观察、第102或98题的授权边界、第29题的局部更新作为已有回归线索。每项核验要指向一个可观察结果，例如“空分析结论进入状态”“新许可与被分析的对象一致”或“旧授权被标记失效”。
3. **冻结一个版本，做小批配对复验。** 先看第93题及上述代表性回归场景，再选少量没有用于调试的基础题，看冲突恢复能否复现。旧题回答修复是否有效，新题回答是否能在另一题里走通。保留原始决策及程序处理记录。发现重复拒绝时沿轨迹定位哪一模块先出现偏差。
4. **达到验收条件后再扩数据。** 同一版本要能完成前述正常、冲突和许可更新三类路径；受控分支至少能按定义执行并得到可比较的结果。若某类条件仍不能可靠复现，日志写下阻塞位置，并按该问题安排下一轮。扩大题量、换模型、改执行器各自对应独立比较。

**本轮交付。** 一份冻结配置、一张三模块核对表、至少一条从条件冲突到重新决策的完整轨迹，以及按基础题列出的结果。当前不预设提升比例。

## 5. 轨迹怎样进入学习

- **监督微调（Supervised Fine-Tuning，SFT）**。以决策当时可见的业务状态为输入，输出经核验的下一步，包括工作类别、处理对象、依据和完成条件。后续轨迹用于验证示范是否成立。同样合理的决策可保留为多个示范。
- **直接偏好优化（Direct Preference Optimization，DPO）**。同一状态下有两条确实可执行的候选决策，重复比较后，一条在规则满足、正确办结或过程推进上有明确较好的表现，才形成偏好对。两条路径相当或排序反转时保留观察。环境异常、执行器误拒和网络中断单列，便于审核数据来源。
- **训练前后比较。** 先准备同接口的原始小模型基线，再比较 SFT 和 SFT 后继续做 DPO 的版本。按基础任务划分训练与测试，同题的状态和续行分支随基础题一起划分。后续轨迹和最终答案用于评价，决策模型输入使用当时可获得的信息。
